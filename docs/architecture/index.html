Architecture · Overview

How Twoje Miejsce fits together

Digital communities for real places: a city, a campus, a housing estate. Members belong to the place, and every feature a place switches on — issue reports, announcements, discussions, or one its admin had the AI write — is a plugin with its own isolated data. One TypeScript codebase: a Bun + Hono API on SurrealDB and an Expo app that runs on iOS, Android and the web.

apps/app Expo app

Expo (React Native) app with Expo Router. The same code renders native views on iOS and Android and HTML on the web (react-native-web, static export). Plugin screens are not written here: they arrive from the API as UI trees and are drawn by src/plugins/Renderer.tsx.

Key files: app/ (routes, thin files) · src/screens/ · src/data/ (TanStack Query hooks) · src/lib/api.ts (Hono RPC client + Better Auth client) · src/lib/config.ts (API address) · src/texts.ts · src/theme/tokens.ts · app.config.ts

Imports: @app/shared (e.g. invite-code helpers at runtime); @app/plugin-sdk and @app/api as types only — AppType comes from the API (a dev dependency), so request and response types are never written by hand.

Never: hand-written fetch (the one exception is the multipart photo upload in src/lib/upload.ts), Polish literals outside texts.ts, Platform.OS in screens, edits to the generated android/ and ios/.

apps/api API & plugin host

Bun + Hono. createApp() in src/app.ts wires the services and is the only place routers are mounted; its return type is exported as AppType for the app's RPC client. The same process hosts plugins (PluginHost) and the AI plugin builder (PluginBuilder).

Key files: src/app.ts · src/server.ts (production entry) · src/test-server.ts (dev and E2E, adds /__test/*) · src/db/ (createDb, schema.ts, query.ts) · src/auth.ts (Better Auth) · src/middleware.ts · src/routes/ · src/plugins/host.ts · src/plugins/builder.ts · src/services/ (ai, db, files, geo, notifications, push)

Imports: @app/shared, @app/plugin-sdk (and its host-side @app/plugin-sdk/engine), and the built-in plugins @plugins/issues, @plugins/announcements, @plugins/discussions.

Public surface (src/index.ts): AppType, createApp, loadEnv. Test code (test-*.ts) is never imported by production code; the build fails if __test ends up in the bundle.

packages/shared app contracts

Zod schemas and types of the app's own API: places and invitations (communities.ts), the user's data (me.ts), maps and geocoding (geo.ts), the plugin builder (builder.ts), plugin lists (plugins.ts), sign-in providers (auth.ts). The API validates requests with them (zValidator); the app reuses the same constants and helpers.

Imports: @app/plugin-sdk (shared shapes such as geoPointSchema and NavigateAction) and zod.

Rule: types and validation live only here (app contracts) and in packages/sdk (plugin contract).

packages/sdk Plugin SDK

The contract between the host and plugins, with three entry points:

  • @app/plugin-sdk — definePlugin, the UI catalog ui, table builders t, loadPlugin, the check result types, and the types plugins use (Context, PluginModule…).
  • @app/plugin-sdk/engine — the host-side runtime of plugin tables on SurrealDB (createDatabase, syncSchema, planSchema). Plugins never import it.
  • @app/plugin-sdk/testing — testPlugin: a plugin tested like a function, on the real engine over embedded in-memory SurrealDB.

Depends on zod, surrealdb and @surrealdb/node. How it works: Plugin runtime.

plugins/* Plugins

Each plugin is one index.ts (its test next to it) that depends only on @app/plugin-sdk and imports nothing at runtime — only import type. Its default export is a factory (sdk) => definePlugin({…}); the host passes the SDK in. That is why the same file can be built in, uploaded at runtime, or written by the AI.

Built in = a dependency in apps/api/package.json + an entry in apps/api/src/plugins/builtin/index.ts (builtinPlugins = [issues, announcements, discussions]).

Uploaded and AI-written plugins never live in this folder: their source is stored in the database. See Checks & AI builder.

scripts/ tooling

  • verify.ts — bun run verify, the only definition of done (see Quality gates).
  • plugin-upload.ts — bun run plugin:upload plugins/<id> [community]: posts the plugin's source to POST /api/admin/plugins of a running API and enables it.
  • adb-reverse.ts — Android over USB: the phone's localhost reaches :4000 and :8081.

Not a workspace package: plain Bun scripts run from the repo root.

demo-video tooling

A Remotion project that renders the demo and the ad from the app's real components (it imports @app/app and @app/plugin-sdk). Not part of the running product.

External services

iOS and Android required

Expo SDK 57 (React Native). The session is a bearer token kept in the Keychain/Keystore through src/lib/storage.ts and sent on every request. The API address comes only from src/lib/config.ts: EXPO_PUBLIC_API_URL at build time, a runtime __API_URL__ (E2E), else http://localhost:4000.

Native config lives only in app.config.ts; android/ and ios/ are generated by expo prebuild.

Web required

The same code exported as static HTML (expo export --platform web). The token is kept in localStorage (via src/lib/storage.ts). The API answers browsers only from TRUSTED_ORIGINS (CORS on /api/*, exposing set-auth-token); native apps send no Origin and authenticate with the bearer token.

E2E tests run against this production export, not the dev server.

Better Auth required

src/auth.ts: e-mail + password, and Google when configured, stored in SurrealDB through the surreal-better-auth adapter (schemaless user, session, account, verification). The bearer() plugin gives web and native one auth path: the Authorization header, no cookies.

Routes: Better Auth owns /api/auth/*; requireUser calls auth.api.getSession() and answers 401 unauthorized without a session.

Services

Built once in createApp() and handed to routes through c.var; plugins reach them only through ctx, filtered by their declared permissions.

  • FileService — uploads (pending → kept), signed URLs, 24 h sweep of unused uploads.
  • AIService — ctx.ai: model calls with a per-installation rate limit.
  • NotificationService — ctx.notify: inbox rows and pushes; resolves "near" audiences itself.
  • OpenGeocoder — address search and reverse geocoding for /api/geo.
  • PluginBuilder — AI-written plugins for a place (versions written in the background).

Each is swappable: createApp({ db, env, ai, push, geocoder, author }) — tests and the E2E server pass fakes.

SurrealDB required

createDb(DATABASE_URL) in src/db/client.ts picks the engine from the URL:

Namespace app, database main. The embedded engine (@surrealdb/node) is loaded only for embedded URLs; the production image does not ship it.

File store

Photo bytes live on disk (DiskFileStore, FILES_DIR or a temp directory); their owner, installation and status live in the plugin_file table. Uploads: JPEG, PNG or WebP, at most 10 MB. The app shows them through short-lived signed URLs (/api/files/:id?exp&sig, HMAC, one hour), so an <Image> needs no Authorization header.

Expo Push Service optional

ExpoPushSender posts to https://exp.host/--/api/v2/push/send; Expo forwards to Firebase Cloud Messaging (Android) and APNs (iOS). EXPO_ACCESS_TOKEN only if the Expo project enables enhanced push security.

Pushes go out in the background: the notification is already in the inbox, so a failing push service never fails the plugin call. Expo Go on Android has no pushes; the app runs without them.

Google sign-in optional

The phone's native account picker returns an ID token; the app posts it to /api/auth/sign-in/social and Better Auth checks it against Google's public keys. No client secret: the API only verifies ID tokens.

Without GOOGLE_CLIENT_ID, GET /api/auth-providers answers { google: null } and the login screen shows no Google button.

Language model optional

One model for the whole host, configured only in src/services/ai/model.ts: an OpenAI-compatible API through Strands Agents (AI_API_KEY + AI_MODEL, optional AI_BASE_URL). It powers ctx.ai (StrandsLanguageModel) and the plugin builder's author agent (StrandsPluginAuthor). An embedding model on the same key and endpoint (text-embedding-3-small, OpenAIEmbeddingModel; it needs only AI_API_KEY) powers ctx.ai.embed.

Without it: the builder answers 503 ai_unavailable, ctx.ai.call throws, and ctx.ai.findSimilar falls back to matching shared words — enough for tests and a keyless demo. Without AI_API_KEY, ctx.ai.embed throws too.

Map tiles optional

The app's map page (src/lib/map/html.ts) loads MapLibre GL JS from unpkg.com (pinned version, checked with SRI) and the OpenFreeMap "Positron" style. On phones it runs in react-native-webview, on the web in an iframe (MapSurface.web.tsx). It draws the map of places, the location picker, and plugin maps (ui.map, via src/plugins/PluginMap.tsx).

The API never talks to the tile servers; only the app's map page does.

Geocoding optional

OpenGeocoder (src/services/geo/open.ts), no API keys: Photon (komoot, OpenStreetMap data) for address search inside Poland; the address at a pin from GUGiK's geocoding service (the national address register), with Photon where GUGiK has none. Used by GET /api/geo/search and GET /api/geo/reverse.

A failing provider answers 502 geocoder_unavailable and the app lets the user place the pin by hand. E2E runs on TestGeocoder (no network).

One request, end to end

Opening a place's dashboard touches every layer: the app's data hook, Hono middleware, the route, the plugin host, the plugins and the database. Step through it with the buttons or the ← → keys.

GET /api/communities/:slug/dashboard

App screen, data hook, renderer
Middleware app.ts
Route routes/communities.ts
PluginHost plugins/host.ts
Plugin widget render(ctx)
SurrealDB platform + plugin tables

  1. The dashboard screen calls useDashboard(slug). The request goes through the Hono RPC client hc<AppType>, so the path, parameters and response type come from the API's own code; tokens.headers() adds Authorization: Bearer …. TanStack Query refetches it every 15 seconds.

  2. createApp() applies CORS to /api/* (origins from TRUSTED_ORIGINS), then one middleware puts the shared services on the context: db, auth, plugins, builder, files, notifications, geocoder. An unhandled error anywhere becomes 500 { error: "internal_error" } (app.onError).

  3. The router starts with requireUser: Better Auth resolves the bearer token to a session (auth.api.getSession({ headers })) — none means 401 unauthorized. A second router middleware awaits plugins.ready(): once per process the host syncs plugin tables and loads uploaded plugins from plugin_source.

  4. memberOf(c, slug) looks the place up by slug and reads the user's role from the membership record, whose id is [community, user]. An unknown place and a place the user does not belong to both answer 404 not_found: a user cannot probe which places exist.

  5. The enabled installations of the place, oldest first — that is the default order of the dashboard and of the place's navigation. Values are always bound through the surql tag.

  6. For every installation (in parallel) the host reads when this user last opened the plugin (plugin_visit, becomes ctx.lastVisit) and builds the plugin's context: the user with their role in this place, the place (with its pin), and only the services the plugin's manifest declares. The rest of ctx rejects on use.

    What exactly is in ctx →

  7. renderDashboardWidget calls each declared widget's render(ctx). The plugin reads its own tables through ctx.db (every query scoped to this installation) and returns a UI tree, not code. The host validates it with dashboardWidgetSchema — a Widget root, read-only: no forms, inputs or tool calls — and signs image URLs.

    A widget that throws or returns invalid UI is logged and left out; null hides it. One broken plugin never breaks the dashboard.

  8. The place's admins may have saved an order (the dashboard row, keys "<pluginId>/<widget>"). sortByOrder puts saved keys first; the rest keep the default order (installation, then declaration).

  9. src/plugins/Dashboard.tsx lays the tiles out on a 2-column grid by their declared size and draws each node with PluginRenderer, which maps the closed node catalog onto design-system components. Tapping a tile navigates to /app/c/<slug>/<plugin>/<view>, where PluginView fetches a full view the same way. Admins long-press to reorder; the order is saved with PATCH /api/communities/:slug/dashboard (requirePlaceAdmin).

Rules for the database

No migration files

The schema is idempotent SurrealQL (DEFINE … IF NOT EXISTS), applied by migrate(): on every start of the dev/E2E server, for every test database, and in production by migrate-cli.js before the server starts. Changes are additive only.

Queries through surql only

Never a plain string: values always go through ${} as bindings. Application code gets a Db from createDb() and uses rows, first, ref, keyOf from src/db/query.ts.

Frontend

One Expo codebase for iOS, Android and the web. Each layer has one job, and code only reaches down. Pick a layer.

HTTP

Routes — apps/app/app/

Expo Router: files are routes, and they stay thin. app/_layout.tsx mounts the providers (TanStack Query, safe area, keyboard, flash messages); app/app/_layout.tsx guards everything under /app with the session (else <Redirect href="/login" />) and registers the phone for pushes.

Routes: /login, /register, /app (dashboard), /app/map, /app/account, /app/invites, /app/create, /app/created, /app/join-code, /app/join-place, /app/preview, /app/scan, /app/c/[slug] (opens the place on the dashboard), /app/c/[slug]/manage, /app/c/[slug]/build, /app/c/[slug]/[plugin]/[view].

Screens — src/screens/

Screen logic, built from the design-system components in src/components/ (which set the roles and labels E2E selects by) and the tokens in src/theme/. Every text comes from src/texts.ts (t.key) — the app is Polish only, no i18n. No Platform.OS here.

Plugin screens are different PluginView has no idea what a plugin shows: it fetches a UI tree from the API, draws it with src/plugins/Renderer.tsx and sends actions back (navigate or call a tool). Dashboard tiles and plugin maps (src/plugins/PluginMap.tsx) work the same way. Server-Driven UI →

Data hooks — src/data/

The only data pattern: TanStack Query. Reads are useQuery; writes are useMutation that invalidates the affected keys. A tool call invalidates every view of that plugin.

Platform and API client — src/lib/

  • api.ts — hc<AppType> (Hono RPC) and the Better Auth client, both sending the bearer token.
  • config.ts — the only place that knows the API address.
  • storage.ts — the only persistent device storage (secure store on phones, localStorage on the web).
  • upload.ts — the one hand-written fetch: multipart photo upload for plugins.
  • *.web.ts / *.web.tsx — platform variants (pushes, Google sign-in, the map surface).

Platform.OS branches are allowed only here and in routes.

The API's types, not copies

import type { AppType } from "@app/api": the client's paths, parameters and response types are inferred from the Hono routers. Change a route and the app stops type-checking until it follows. Messages from the API never reach the UI directly; screens show their own t.* texts (plugin content is the exception: it is the plugin's Polish).

Quality gates

A task is done only when bun run verify exits 0 (scripts/verify.ts). The five checks (lint … schema) are independent and run concurrently, each printing its output when it finishes; then build, e2e (on the web export the build just made) and android run in order. Any failure ends the run with a non-zero exit after the summary. Pick a stage.

lint + format bun run lint

biome ci --error-on-warnings . — Biome lints and checks formatting of the whole repo (these HTML pages included); warnings fail too. No global rule switches; a local biome-ignore needs a reason.

biome.json enforces several AGENTS.md rules mechanically: Platform and DOM globals outside src/lib/, navigation and storage imports, JSX text literals and Polish string literals outside texts.ts in the app, SurrealQL without the surql tag (biome-plugins/*.grit), test-*.ts imports in API code, Node modules and undeclared dependencies in plugins and packages/shared, floating promises.

typecheck bun run typecheck

tsc -p . in every workspace, in parallel (bun run --parallel --no-exit-on-error --filter '*' typecheck), each plugin included. This is also where the app learns about a changed API: its client is typed by AppType.

unit bun scripts/bun-test.ts ./packages ./plugins ./apps/app/src ./apps/api/src

Pure logic next to the code. Plugins are tested with testPlugin: the real engine on embedded in-memory SurrealDB, with requires, Zod input parsing and UI schemas applied like in the host — no API, no AI model.

integration bun scripts/bun-test.ts ./apps/api/test

Every test calls setup(): a fresh database (schema applied) on the one embedded in-memory engine of the process, and the API through app.request() — no ports. close() in afterEach. AI, push, geocoder and the plugin author are fakes passed to createApp.

One engine per process on purpose: with @surrealdb/node 3.0.3, Bun 1.4 crashes on exit after a second embedded engine or REMOVE DATABASE. Never open another mem:// connection in tests (docs/testing.md). That makes the crash rare, not impossible, so both test stages run through scripts/bun-test.ts, which counts a SIGSEGV after a summary with "0 fail" as green (with a note) and keeps every other exit code.

schema bun run db:check

On a clean embedded database, in memory and on disk (surrealkv): the schema applies, applying it again is a no-op, every platform table exists, and the built-in plugins' tables sync — a second plan contains only idempotent statements.

e2e bun run e2e

Playwright on the production static web export (expo export, served by scripts/serve.ts on a random port). Each worker starts its own API (apps/api/src/test-server.ts, mem://, a free port) and every test begins with POST /__test/reset. Tests select by roles and labels, which is why the components set role, aria-level, aria-label. Inside verify the stage serves the build stage's dist/ (E2E_PREBUILT=1); a plain bun run e2e exports first.

/__test/* exists only in test-server.ts, which refuses to start outside NODE_ENV=test. Native screens are covered by the Android and iOS builds, not on-device E2E.

build bun run build

API: Bun.build of server.js and migrate-cli.js, plus plugin-types.json (the SDK types the plugin type check reads, since the image has no repo); it fails if __test ended up in the bundle. Then the web export of the app.

android bun run android

expo prebuild + assembleDebug. Needs JAVA_HOME, ANDROID_HOME, ANDROID_NDK_HOME: run the full verify inside nix develop .#android.

A skip is not green VERIFY_SKIP=android,e2e marks stages SKIP in the summary; a task reported with a skipped stage must say which and why.
