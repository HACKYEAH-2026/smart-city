Plugin runtime

How a plugin actually runs

Every feature of a place (issue reports, announcements, discussions, the plugins the AI writes) is a plugin: one TypeScript file that imports nothing at runtime, gets the SDK from the host, declares its tables, views, widgets and tools, and reaches the world only through ctx. This page follows that file from loading to a resident's tap, with the real code paths.

One file, no runtime imports

The default export is a factory (sdk) => definePlugin({…}). The host hands in the SDK.

Only ctx

No app database, no disk, no network. Services exist only if the manifest declares them.

Isolated per installation

Every query, reference and live event is scoped to one plugin × community.

UI is data

Views return a JSON tree from a closed catalog. The app renders it; actions are data too.

The mental model

Three things are easy to mix up: the plugin (code with an id), the installation (that plugin enabled in one community: a plugin_installation row) and the context (ctx, built for every single request from the installation, the signed-in user and their role in that community).

Anatomy of a plugin file

A complete, working plugin. Click the numbers to see what the host does with each part. The built-in plugins in plugins/ follow exactly this shape; plugins/announcements/index.ts is the closest real one.

Type-only imports

import type is erased at compile time, so the module has no runtime dependencies. The imports check stage rejects any value import, including import { z } from "zod" (apps/api/src/plugins/check.ts).

That is what lets the same file run built in, uploaded at runtime, or later in a Worker/WASM sandbox.

The factory receives the SDK

The host calls the default export with one frozen object: { definePlugin, ui, z, fileRef, geoLocation, t } (sdk in packages/sdk/src/load.ts). Frozen, because every plugin gets the same objects: one plugin must not be able to replace ui.card under the others.

loadPlugin wraps the call: a factory that throws becomes PluginError("Plugin factory threw: …").

Declared tables

t.table(columns, { indexes, unique }). The host turns each into one physical SCHEMAFULL table, p_notes__notes, shared by every installation of the plugin, and syncs it without migration files (see schema evolution).

The type of ctx.db.notes (inserts, filters, with expansions) is inferred from this object by definePlugin.

Manifest

Parsed with pluginManifestSchema: id matches ^[a-z][a-z0-9-]{1,39}$, name 1–60 chars, version semver, icon ≤ 8 chars (default 🧩), description ≤ 280.

The id is the registry key; uploading a plugin with a built-in id is rejected.

Permissions

A subset of "db", "files", "ai", "notify". A service that is not declared is still on ctx, but every use of it rejects with Plugin did not declare the "…" permission. Try it in ctx: the only door.

Navigation

At least one entry. loadPlugin checks that every nav.view is a function in views: Nav entry "…" points to missing view "…".

GET /api/communities/:slug/nav lists the entries of the enabled plugins in installation order; the app polls it every 5 s, so a newly enabled plugin shows up without a reload.

A view

(ctx, params) => UINode. params are flat strings from the query string. The result must be a Screen at the root: the host validates it with screenSchema, and an invalid tree is a plugin error (500 for that request only).

Rendering a view records a visit, which becomes ctx.lastVisit next time.

Actions are data

ui.tool("add") is just { type: "tool", tool: "add" }. The app merges the form's field values into its args and POSTs them. ui.navigate(view, params) is { type: "navigate", … } and opens another view of the same plugin.

Dashboard widgets

Every plugin has exactly one (checked on load): its tile is how residents open the plugin. A fixed size on a two-column grid (w 1–2, h 1–3) and a render(ctx) that always returns ui.widget(…) (an empty state when there is no data yet).

Widgets must be read-only (dashboardWidgetSchema): no forms, inputs or tool actions anywhere in the tree. A widget that throws is left out; the rest of the dashboard renders.

Input is a Zod schema

The host parses args with it before the handler runs; invalid input answers 400 invalid_input with the Zod issues. The handler gets z.output, with defaults applied. Messages for residents go in the schema, in Polish.

The handler

Runs inside guard(). It returns a ToolResult: toast, error, navigate, refresh, close, data (validated with toolResultSchema). Returning nothing means {}.

Expected problems (not found, not allowed) are returned as { error: "…" }, not thrown.

Role check

requires: "admin" is enforced by the host before input parsing: non-admins get 403 forbidden. The role is per community (membership.role). Rules like "author or moderator" are checked in the handler instead.

Default export

Built-in plugins are listed in apps/api/src/plugins/builtin/index.ts; uploaded and AI-written ones arrive as source text and go through the six check stages first. All of them end up in loadPlugin.

  1. Built-in plugins are ordinary workspace packages (@plugins/issues, @plugins/announcements, @plugins/discussions) imported by the API and listed in one array. Importing them runs nothing: the module only defines a function.

  2. The same function is used by the API host and by the test harness, so a plugin that loads in tests loads in production. Each step throws a PluginError with a message meant for the plugin's author (a person or the AI builder).

  3. createApp builds one PluginHost with the services plugins may get (db, files, AI, notifications). Its constructor loads every built-in synchronously and keeps them in a Map keyed by plugin id, marked origin: "builtin".

  4. Once per process, before the first plugin request (the communities router awaits it in a middleware): syncPluginTables for every built-in, then every row of plugin_source (plugins uploaded at runtime or published by the AI builder) is compiled, synced and registered as "uploaded". A stored plugin that no longer loads is logged and skipped, so one broken upload never takes the API down.

  5. PluginHost.enable(plugin, community) runs when a place is created with chosen built-in plugins, when a place admin switches one on (PUT /api/communities/:slug/plugins/:id), when an AI plugin is published, or through the admin API. Re-enabling flips enabled back on and keeps the data.

  6. Only when the INSERT IGNORE actually created the installation. ctx.user is SYSTEM_USER ({ id: "system", role: "admin" }, no account): rows get createdBy: null, it cannot be stored in a t.ref("user") column and cannot attach pending uploads.

    From now on the plugin appears in the place's navigation and dashboard, and its views and tools answer.

    ctx: the only door

    createPluginContext builds a fresh context for every view, widget, tool call and onInstall. Toggle the manifest's permissions and see what the plugin gets.

    Manifest

    Permissions

    Why a Proxy and not undefined deniedService(permission) (packages/sdk/src/denied.ts) returns a Proxy that is callable and returns itself for any property, so ctx.db.items.findMany() type-checks and fails with a clear message at the call, not with "cannot read property of undefined". It answers undefined for then, so await ctx.db does not hang.
    What is never on ctx The app database, e-mail addresses (a t.ref("user") expands to { id, name }), the disk, the network, residents' saved places and live positions. ctx.notify resolves recipients inside the host and returns nothing about them, not even a count.

    Isolation: one table, many communities

    A plugin's table is one physical SurrealDB table shared by every community that enabled the plugin. Isolation comes from the engine, not from separate databases: every row carries installation, and every statement the engine builds is restricted to the current one. Pick the installation a request runs in.

    Physical table p_issues__issues

    id installation (plugin_installation:…) title status

    What the plugin's code sees

    • Reads: WHERE installation = $installation AND … on every SELECT, count, UPDATE … WHERE and DELETE … WHERE. A row of another community is simply not there: get → null, update → null, delete → false.
    • References: before a write, every t.ref value is looked up. A row of the plugin's own table must have the same installation (DbError: issues.x: unknown issues id), a user must exist (unknown user), a file must belong to this installation (unknown file).
    • Indexes: every declared index and unique is prefixed with installation, so "unique" means unique within one community.
    • Live queries: watch() drops notifications whose row belongs to another installation.
    • Lifecycle: installation is record<plugin_installation> with REFERENCE ON DELETE CASCADE. Deleting a place cascades to its installations, and from there to every plugin row and file of that place.

    ctx.db → SurrealQL

    Plugins never write SurrealQL. createDatabase (packages/sdk/src/engine/client.ts) turns typed calls into surql statements whose values are always bound variables. Build a query and see the statement the engine sends (the same code runs in the host and in testPlugin). The table is the issues example from docs/plugins.md.

    Query

      Writes

      Writes validate every value against the column (DbError for a missing required column, a wrong type, an unknown enum value or column), check references, and run as one transaction together with the confirmation of any pending file they reference. A retryable conflict is retried up to 5 times. 

      await ctx.db.issues.insert({ title: "Latarnia", reporter: ctx.user.id });
      RETURN [record::exists($bind__1)];   -- the user ref exists

BEGIN TRANSACTION;
LET $result = (CREATE $bind__2 CONTENT $bind__3 RETURN AFTER);
COMMIT TRANSACTION;
RETURN $result;

      $bind__2 is p_issues__issues:⟨uuid⟩; $bind__3 holds the values with defaults applied (status: "open", votes: 0) plus installation, created_at, updated_at and created_by. null values are left out (stored as NONE). 

      await ctx.db.issues.update(id, { status: "fixed" });
      BEGIN TRANSACTION;
LET $result = (UPDATE $bind__1 SET status = $bind__2, updated_at = $bind__3
               WHERE installation = $bind__4 RETURN AFTER);
COMMIT TRANSACTION;
RETURN $result;

      A patch: only the given columns; null clears an optional column (= NONE). The WHERE installation makes an id of another community a no-op that returns null. 

      await ctx.db.reports.upsert(
  { issue: issue.id, author: ctx.user.id, description },
  { on: ["issue", "author"] },  // must equal a declared unique
);
      BEGIN TRANSACTION;
LET $existing = (SELECT VALUE id FROM p_issues__reports
                 WHERE installation = $i AND issue = $a AND author = $b LIMIT 1)[0];
LET $result = (IF $existing { (UPDATE $existing SET … RETURN AFTER) }
               ELSE { (CREATE $new CONTENT … RETURN AFTER) });
COMMIT TRANSACTION;
RETURN $result;

      Simplified (bindings named for reading). Matched on the values that will be written, defaults included, so an omitted column cannot widen the match; a concurrent duplicate fails on the unique index. 

      await ctx.db.issues.delete(id); // → boolean
      DELETE $bind__1 WHERE installation = $bind__2 RETURN BEFORE;

      References decide what happens to rows pointing here: required refs cascade, optional ones are unset, onDelete: "restrict" rejects the delete (DbError: … the row is still referenced (restrict)).

      watch(): live queries

      watch() opens a SurrealDB LIVE query on the plugin's table, takes a snapshot with findMany semantics, then turns raw notifications into events relative to the rows the subscriber already has. Change the data and watch what the subscriber receives.

      Data in this installation

      id title status Actions

      Subscriber

      for await (const event of ctx.db.issues.watch({ where: { status: "open" } })) { … }

        Rows the subscriber has:

        • The first event is always { type: "snapshot", rows }; orderBy and limit (default 100) apply only to it.
        • A row entering the filter is a create, a change to a row the subscriber has is an update, a row leaving the filter or deleted is a delete; anything else is skipped.
        • Cascades are streamed too: deleting a discussion yields a delete for each of its messages.
        • The generator never ends by itself; break or return() unsubscribes and kills the live query.
        • Plugins expose watches as streams. They run in the test harness; the API has no HTTP transport for them yet, so the app refreshes by polling and by invalidating queries after tool calls.

        What the app does

          The catalog

          A new node type means three edits in one commit: its Zod schema and builder in packages/sdk/src/ui.ts and a branch in apps/app/src/plugins/Renderer.tsx. An older app that meets an unknown node shows "Ten element wymaga nowszej wersji aplikacji." instead of crashing.

          Layout ui.stack, ui.row, ui.list(label, items), ui.card({ title, subtitle?, badge?, onPress?, children? })
          Content ui.heading, ui.text, ui.badge, ui.progress, ui.stat, ui.empty, ui.image(fileId, alt), ui.highlight, ui.activity({ title, text?, person?, at?, unread? }), ui.map({ label, layers, center?, zoom? }) with ui.map.pins / routes / areas

          Files, AI and notifications

          The three services beyond the database. Each is created per installation by the host, so a plugin can only ever touch its own files, spend its own AI budget and notify members of its own community.

          1 · Pickui.imagePicker in a form; the app uploads before submit
          2 · UploadPOST …/plugins/:id/files, JPEG/PNG/WebP ≤ 10 MB → file_<uuid>, status pending
          3 · Validatetool input fileRef() (format check, typed FileId)
          4 · Keepa t.ref("file") write confirms it (kept) in the same transaction
          5 · Showui.image(fileId); the host adds a signed URL (HMAC, 1 h)
          • Only the user who uploaded a pending file may reference it (DbError: … file was uploaded by another user); once kept, any row of the installation may.
          • Uploads never referenced are deleted after 24 h (swept on the next upload). Bytes live in a FileStore on disk, metadata in plugin_file.
          • ctx.files.info(id) and ctx.files.remove(id) only accept files of this installation.
          • Upload is the app's only hand-written fetch (apps/app/src/lib/upload.ts): multipart has no RPC types.

  text: (i) => `${i.title}. ${i.description}`,
  limit: 1,

const vector = await ctx.ai.embed(input.title); // number[]: stored and compared by the plugin
          • The model is host configuration: Strands Agents on an OpenAI-compatible API (AI_API_KEY, AI_MODEL, optional AI_BASE_URL; apps/api/src/services/ai/). Plugins never see keys.
          • At most 60 calls per minute per installation; images are read only from this installation's files.
          • embed uses OpenAI's text-embedding-3-small on the same key (without AI_API_KEY, it throws): text up to 8000 characters, at most 600 per minute per installation, counted apart from calls. Vectors of different models are not comparable.
          • findSimilar sends at most 30 candidates and keeps matches scoring ≥ 0.6. Without a model it falls back to shared words (score ≥ 0.5), so tests and a keyless demo still work.
          • With a schema, the answer is parsed with it; tests use plugin.ai.mockCall / mockSimilar / mockEmbed.

  to: { near: { lat: input.lat, lng: input.lng, radius: 500 } }, // or { users: [...] } or { everyone: true }
  title: "Dzik z młodymi przy placu zabaw",

          • Validated like a tool input (parseNotification): title 1–120, body ≤ 500, radius ≤ 50 000 m, open must be a view of this plugin. An invalid call throws and the tool fails with 500.
          • The host resolves recipients in one INSERT INTO notification (SELECT … FROM membership …): members of this community only, never the sender; near matches saved places and positions shared in the last 30 minutes.
          • The plugin gets nothing back, not even a count, so it cannot be used to locate anyone.

          Testing a plugin without the API

          testPlugin from @app/plugin-sdk/testing runs a plugin against the same engine on embedded in-memory SurrealDB (platform tables included), with the same loadPlugin, permission proxies, requires, Zod parsing and UI/result schemas as the host. No API, no model, a fresh database per test.

          The full harness API (.as(user), .files.fake(), .stream(), .setNow(), .notifications(), .deleteUser()…) is in docs/plugins.md.
