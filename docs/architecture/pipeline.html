Plugin pipeline

From source code to a running plugin

Plugin code reaches the API in three ways: compiled in, uploaded by the platform admin, or written by AI for one place. Uploaded and AI-written code passes the same six checks before anyone can use it, and its tables change only in ways that keep every stored row valid.

This page follows the code. What a loaded plugin can do at runtime — ctx, isolation per community, the ctx.db engine, Server-Driven UI — is on Plugin runtime; the system as a whole is on the Overview.

Three ways in, one gate

Every plugin ends up in the same registry: a Map inside PluginHost (apps/api/src/plugins/host.ts), keyed by plugin id. Pick a path to see who uses it and what it goes through.

uploads and AI versions
PluginHost.validate(source) syntax → imports → types → safety → load → schema. check() stops here and stores nothing; upload() goes on: sync the tables, store the source, register.
registered
Registry: Map<id, LoadedPlugin> origin "builtin" or "uploaded"; enabled per place in plugin_installation

Built-in plugins

  • A package in plugins/<id>/ that depends only on @app/plugin-sdk, a dependency in apps/api/package.json and an entry in apps/api/src/plugins/builtin/index.ts: builtinPlugins = [issues, announcements, discussions].
  • The PluginHost constructor runs loadPlugin(mod) on each one: the manifest, nav → views, dashboard widgets, tables, tools and streams are validated. The source stages (syntax, imports, types, safety) do not run: this code is type-checked, linted and tested with the repo by bun run verify.
  • Their tables are synced on the first ready() of the process.
  • Their ids are reserved: an upload that claims one fails the load stage with "issues" is a built-in plugin.
  • They are the only plugins offered to every place: the new-place wizard and GET /api/plugins list built-ins only.

Admin upload

  • For the platform admin, who holds PLUGIN_ADMIN_TOKEN (at least 24 characters). Without the token in the env, every admin route answers 404.
  • POST /api/admin/plugins { source }: one TypeScript file, up to 200 000 characters (PLUGIN_SOURCE_MAX). In dev, bun run plugin:upload plugins/<id> [community] uploads the package's index.ts and enables it in a community (default krakow).
  • PluginHost.upload() = validate() → sync the tables → store the source in plugin_source → replace the registry entry. No restart; the next request runs the new code.
  • Trust model: the token grants full trust, because the code runs inside the API process (see Safety).

AI builder

  • For a place's admin, in the app: Zarządzaj miejscem → Rozszerzenia → „Dodaj rozszerzenie” → „Stwórz rozszerzenie z AI”. They describe the feature in their own words.
  • An agent writes the plugin and runs PluginHost.check() on it, up to 8 times, until a version passes; the host then checks the final source again itself.
  • Publishing = PluginHost.upload() (every check again) + enable(), in that place only. Details in The AI plugin builder.

              The result is for the author
              

                PluginCheck is { status: "ok", plugin } (what the plugin declares, so the author
                can confirm it is what they meant) or { status: "error", stage, errors }. At most 10 issues
                (MAX_CHECK_ISSUES, the rest counted as “…and N more”); line and
                column are 1-based and snippet is that source line, trimmed. The author may be a
                person or the AI agent: both read the same messages.
              

            

            

              types and safety block the API
              

                Both compile TypeScript synchronously in the API process; while they run, the API answers nothing else.
                docs/plugins.md puts it at ~1–2 s per check, the first one in a process much
                longer (the type checker loads the compiler and the SDK types; the builder warms it up at start). Warm
                checks of the samples above took 0.13–0.17 s on a dev laptop. The fix on the list: run checks in a
                Worker.
              

            

          

        


        
        

          
Safety: a static guard, not a sandbox

          

            A plugin runs inside the API process. The contract keeps it to ctx and the SDK — no imports, no
            globals — and the safety stage rejects the known ways around that contract. Every message below

'.constructor' is not allowed in plugins: it reaches the host's constructors and prototypes

              

                (async () => {}).constructor is the classic way from any function to a code-evaluating
                constructor; property descriptors would let a plugin redefine shared objects.
              

            

            

              
Strings that name them

              
const key = "constructor";
const value = record[key];

              
The string "constructor" is not allowed in plugins: it names a host global or an unsafe property

              

                Computed access (o["constructor"]) would sidestep the property check, so a string literal (or a
                template without substitutions) that equals one of the names above is rejected. Only exact matches: a
                label such as "Mój proces" is fine, but a string that is exactly "module" or
                "self" is not.
              

            

            

              
Calls through any or Function

              
const run: any = loadSomething();
run();
if (typeof f === "function") f(); // f: unknown → Function

              
Calling a value of type 'any' or 'Function' is not allowed: give it a function type

              

                The type checker cannot vouch for what such a call reaches. Calls, new and tagged templates
                are checked; give the value a real function type instead.
              

            

            

              
Changing objects the plugin did not declare

              
JSON.parse = (s: string) => s;
Math.random = () => 4;

              
Changing 'Math.random' is not allowed: a plugin cannot modify built-in objects

              

                An assignment (any =, +=…), ++/-- or
                delete on a member chain is allowed only when the chain starts at a name the plugin declared
                itself (a variable, parameter, function, class or destructured binding). Built-ins are shared by every
                plugin and by the host.
              

              
const counts: Record<string, number> = {};
counts.open = 1; // fine: the plugin's own object

            

            

              
Ambient declarations

              
declare const Bun: { env: Record<string, string> };
namespace Tools { export const x = 1; }

              

                Ambient declarations ('declare', 'namespace', 'module') are not allowed: a plugin gets only ctx and the SDK
              

              

                declare would tell the type checker that something exists when it should not (here
                Bun is also reported as a host global).
              

            

            

              
import.meta

              
const m = import.meta;

              
'import.meta' is not available to plugins

              
It describes the module on the host's disk (its path, its environment), which a plugin has no business knowing.

            

            

              
@ts-ignore, @ts-expect-error, @ts-nocheck

              
// @ts-expect-error
const n: number = "x";

              
'@ts-expect-error' is not allowed: plugin code must type-check

              
Switching the type checker off would switch off these checks too, since they rely on the types.

            

          


          
Two more guards, at runtime

          

            

              
A frozen SDK

              

                sdk = Object.freeze({ definePlugin, ui, z, fileRef, geoLocation, t }), each part frozen too
                (also ui.map; z is a module namespace, immutable already). Every plugin gets the
                same objects, so one plugin must not be able to swap ui.card or t.text under the
                others.
              

              
packages/sdk/src/load.ts

            

            

              
Undeclared permissions

              

                A ctx service missing from permissions is a Proxy that rejects any use, at any
                depth, with Plugin did not declare the "ai" permission. It is not thenable, so
                await ctx.db does not hang.
              

              
packages/sdk/src/denied.ts

            

          


          

            The honest trust model
            

              Uploaded plugins run inside the API process: the admin token grants full trust (“trusted administrator”).
              Plugins written by AI for a place run there too — and the load stage executes their source
              during every check, including each attempt of the AI author, before a person has read it.
              safety rejects the escape hatches it knows; a determined author may find one it does not. The
              contract was built for isolation (no runtime imports, everything through the async ctx), so
              moving plugins into a Worker/WASM sandbox — on the README roadmap — changes the host, not plugin code.

Schema evolution without migrations

          

            There are no migration files. A plugin declares its tables; on every load the host compares the declaration
            with the shape it stored last time and either applies the difference in one transaction or rejects the whole
            version. The rule: every row already stored must stay valid.

  notes: t.table(
    {
      title: t.text(),
      body: t.text().default(""),
      status: t.enum(["open", "done"]).default("open"),
      author: t.ref("user").optional(),
    },
    { indexes: [["status"]] },
  ),
},

How it works

          

            

              
One physical table per plugin table

              

                p_<plugin>__<table> (a hyphen in the id becomes _), SCHEMAFULL, shared
                by every installation of the plugin. Each row carries installation (a record that cascades on
                delete), created_at, updated_at, created_by.
              

            

            

              
Indexes start with the installation

              

                FIELDS installation, … on every index, so unique means “unique within one
                community” and every index serves one community's queries.
              

            

            

              
The stored shape

              

                plugin_schema:<physical table> keeps what was declared — per column kind,
                nullable, enum values, ref target and onDelete — and
                the index names. Changes are compared against this, not against the database's own metadata.
              

            

            

              
One transaction, every community

              

                A sync is applied all at once or not at all. The tables are shared, so a change applies to every community
                that uses the plugin, at the same moment.
              

            

            

              
When it runs

              

                On start (ready(): built-in and stored plugins), on every upload and AI publish, as a plan
                only in every check, and in the test harness (testPlugin syncs on a fresh database).
              

            

          


          

            The first sync of the table above (a fresh database)
            
DEFINE TABLE IF NOT EXISTS p_notes__notes SCHEMAFULL;
DEFINE FIELD IF NOT EXISTS installation ON p_notes__notes TYPE record<plugin_installation> REFERENCE ON DELETE CASCADE;
DEFINE FIELD IF NOT EXISTS created_at ON p_notes__notes TYPE datetime;
DEFINE FIELD IF NOT EXISTS updated_at ON p_notes__notes TYPE datetime;
DEFINE FIELD IF NOT EXISTS created_by ON p_notes__notes TYPE option<record<user>> REFERENCE ON DELETE UNSET;
DEFINE INDEX IF NOT EXISTS p_notes__notes__created ON p_notes__notes FIELDS installation, created_at;
DEFINE FIELD IF NOT EXISTS title ON p_notes__notes TYPE string;
DEFINE FIELD IF NOT EXISTS body ON p_notes__notes TYPE string;
DEFINE FIELD IF NOT EXISTS status ON p_notes__notes TYPE "open" | "done";
DEFINE FIELD IF NOT EXISTS author ON p_notes__notes TYPE option<record<user>> REFERENCE ON DELETE UNSET;
DEFINE INDEX IF NOT EXISTS p_notes__notes__i_status ON p_notes__notes FIELDS installation, status;
UPSERT plugin_schema:p_notes__notes SET columns = { …stored shape… }, indexes = ["p_notes__notes__i_status"];

            

              Note what is not there: no DEFAULT clauses. Defaults are applied by the engine when a
              plugin inserts a row, which is why changing a default needs no statement at all.

                    request listed for context, and gets the next version string (1.1.0, 1.2.0…).

                    madeByAi: true), but only in its own place: the catalog lists built-ins only, and the
                    place routes accept an AI plugin only if this place published it. A later version runs once it is
                    published again; the plugin id stays, so its tables and data stay — the
                    schema rules decide whether the new version may publish.

                → change, publish →
                published = n + ksame id, same data
              

            

          


          

            

              
What admins see

              

                GET /api/communities/:slug/plugins lists the built-in plugins, then the place's AI plugins:
                drafts with draft: true (named after their latest ready outline, or the request), with
                working while a version is written. A draft cannot be switched on; it is enabled by
                publishing.
              

            

            

              
The model

              

                Strands Agents with an OpenAI-compatible model (AI_API_KEY, AI_MODEL, optional
                AI_BASE_URL) from services/ai/model.ts. With a model configured,
                the plugin type checker warms up in the background when the API starts.
              

            

            

              
Tests never call a model

              

                TestPluginAuthor (apps/api/src/test-author.ts; in E2E via
                PLUGIN_AUTHOR=test in test-server.ts) writes a fixed board of notes
                named after the quoted text in the request, and checks it like the real author. firstTry: "typo"
                makes its first check fail on ctx.db.notez to exercise the loop.
              

            

          

        


        
        

          
Known limits

          
From the Known issues of docs/plugins.md, with the planned fix.

          

            

              
A static guard, not a sandbox

              
safety knows the escape hatches it knows. AI-written plugins run with the same trust as uploads.

              
fix Plugins in a Worker/WASM sandbox (README roadmap).

            

            

              
Checks block the API

              

                types and safety compile synchronously; the AI author runs up to 8 checks per
                version.
              

              
fix Run checks in a Worker.

            

            

              
Modules are never unloaded

              

                Every check that reaches load imports a new module; an agent iterating on a plugin grows
                memory.
              

              
fix Run load in a disposable Worker.

            

            

              
onInstall has no real user

              

                The system user has no account: seeded rows get createdBy: null, it cannot fill a
                t.ref("user") column or attach uploads.
              

              
workaround Optional user refs for seeded rows.

            

            

              
The test harness db is untyped

              
testPlugin().db gets the module, not its table types: plugin.db.items!.

            

            

              
One embedded engine per test process

              

                Never open another mem:// connection in tests: with @surrealdb/node 3.0.3, Bun 1.4 crashes on
                exit. See docs/testing.md.
